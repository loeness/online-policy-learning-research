# V2：失效归因与定向优化

2026-10-15。用户要求具体展开验证并优化当前失效算法。保留全部 V1 结果，不据新结果改写原假设或删除失败。原 V1 的累计回报仍是该实现的真实表现，但后述实现缺陷使它不能单独证明知识组织思路无效。

## 已确认问题与待验证假设

1. **局部更新被误回滚。** V1 新分配情境槽时，先清除该行，再重新安装整个旧 committed 矩阵，抹掉其他行尚未整合的试用更新。修正只清除新槽，其余行逐位保持。用单因素对照量化修复的贡献；修 bug 不算论文创新。
2. **路由分裂。** V1 的复用和新建证据不对称，多个带局部信息的原型难以正确复用。V2 使用有界一致后缀、全部共同支持单元的兼容性判断、未知单元不作矛盾、暂存与持久库分离。目标是降低误分裂，同时不靠全部 abstain 获得高纯度。
3. **局部学习与共享接受被混合。** V1 共享候选失败时会回滚本周期全部局部学习。V2 先以独立 int8 保留 PPO 局部更新，再决定是否有更省字节的共享编码。共享不通过时保留独立编码。
4. **经验收益评分并非严格策略改进证据。** V1 gate 在 trial 策略采样的数据上使用 candidate/incumbent 比值；与实际行为采样分布不一致。记录使用实际 behavior 概率的诊断评分，但不把它当安全保证。V2 的结构接受只声称动作分布失真受限，不用噪声收益符号阻止所有局部学习。

## 实验一：因果归因

同一个 W0、PPO、隐藏切换安排及相同交互预算。六条件：

| 条件 | 路由 | 分配语义 | 编码 | 回答的问题 |
|---|---|---|---|---|
| learned_int8 | 原无标签路由 | 原实现 | int8，320 B上限 | 复现旧方法 |
| learned_int8_preserve_trial | 原无标签路由 | 修正 | 同上 | 误回滚造成多少损失 |
| oracle_int8 | 真值，仅诊断 | 无槽重用 | 同上 | 消除辨识错误后是否能学会 |
| learned_dense | 原无标签路由 | 原实现 | dense，664 B | 压缩是否是主要瓶颈 |
| oracle_dense | 真值，仅诊断 | 无槽重用 | dense，664 B | 相同优化器/表示的诊断参考 |
| oracle_gate | 真值，仅诊断 | 无槽重用 | 原门控 | 路由正确时门控是否仍妨碍学习 |

Oracle 只作归因参考，不计作满足未知情境约束的方法，不用它宣称与无标签算法同等信息。dense 使用较大容量，不能据其优势宣布同预算改进。

Pilot：seed787、每条件8,192步。正式：新 seeds541/557/569、每条件32,768步；本协议在正式前提交。pilot用于软件正确性与排除无意义配置，不按正式结果选择学习率、窗口或最好种子。所有原训练设置不变，3个fit rollout＋1个holdout，所有成本计入。完整逐步日志及实际执行的 monkeypatch/factory 配置和源码快照保存。既有旧重访函数不执行。

## 实验二：无标签辨识优化

新 EvidenceRouter 与原接口一致，从空库开始，最多六原型，窗口32。先在保存的原行为流上比较，零新增环境交互；这批流是开发诊断数据，不能作为独立泛化测试。报告覆盖、ARI、generation纯度、分配/驱逐、复用、歧义和时间。反对“只提高纯度”的成功标准：只有覆盖不比原W32降低超过5百分点且分配/驱逐显著减少，才称发现机制有所改善。未通过也保留失败。

## 实验三：新种子在线闭环

使用相同新 seeds541/557/569、32,768步和外部切换安排，五条件：单头在线更新、修复分配的原路由int8、修复分配的新路由int8、新路由＋原门控、新路由＋非阻塞共享整合。前三项分别回答简易学习基线、实现修复、辨识机制；后三项隔离路由及结构接受的作用。

非阻塞整合：独立int8作为局部学习的保留编码；共享候选只有在实际字节更少，且在有界旧anchor与当前留出观测上的 mean KL≤.002、max KL≤.02时替换。候选上限取 min(320, int8_bytes−1)，避免以更多字节换效果后声称压缩。候选仅从均值残差、双原型残差和SVD选；没有候选通过就使用int8。这是受控策略压缩，不是有值函数保证的安全改进。

本轮首先验证作用机制，仍报告完整恢复包、W0、router、replay、optimizer与临时区；不将320 B修正包说成全智能体容量。新正式方法附加检查 W0文件＋checkpoint≤256 KiB 的恢复包边界；超出则明确报不满足而不隐式删除数据。工作区单独计量；该恢复包边界不等于任意运行时内存的理论上限。

判断顺序：先看oracle诊断是否显著改善；再看修bug的贡献；再看新路由是否提高同流表现；最后要求新结构规则相对同路由int8或单头的累计回报、字节与时间形成可复核权衡。即使效果提高，也先扣除实现修复和已有压缩技术的贡献，再评价创新。
